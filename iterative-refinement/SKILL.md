# Iterative Refinement（迭代求精闭环）

## 概述

将任务组织为五个阶段的闭环：目标量化 → 计划分解 → 分步执行并即时验证 → 整体审查与对抗性反驳 → 按批评迭代，直至满足全部验收标准或达到轮次上限。设计借鉴 evaluator-optimizer 工作流，并吸收自我纠错文献的证据：外部可验证信号优先于自我反思。

## Phase 0：目标与验收标准

进入任何执行前，必须先有可判定的验收标准：

- 标准应是可执行的验证：测试命令、量化阈值（准确率、覆盖率、抽样误差条数）、产物约束（路径、格式）、证据数量（核对条数、引文条数）。
- 用户未给出标准时，先提出 2–5 条建议标准请其确认或修改，确认后才进入 Phase 1。标准模糊时不许自行宣布达标。
- 用户授权由智能体自拟标准时，可以照拟，但须在交付报告中声明"验收标准由智能体拟定、经用户授权"，以便用户知情其置信权重。
- 同时与用户确认：迭代轮次上限（默认 3 轮）、遇到何种阻塞需停下来请示。

## Phase 1：计划分解

- 将目标拆为 3–8 个可独立验证的步骤，每步附明确的"完成判据"。完成判据与验收标准一样须可判定（可执行、可比对），不接受"看起来没问题"式模糊判据。
- 环境预检：正式执行前确认所需工具、数据、权限可用（打印版本号、试读样本数据、测试写权限）；预检不通过则此时就报告缺失项，不进入 Phase 2 硬闯。
- 把计划写入任务工作目录下的计划文件（模板见 assets/plan-template.md）：统一命名为 plan.md、置于任务工作目录根部，每步标注状态：pending / in-progress / verified / failed。跨会话续作时首先读取该文件恢复进度，禁止凭记忆续作。
- 高风险或不确定性大的步骤优先安排，或先做小规模可行性验证再正式排入计划。对"一处错则全局失效"的关键步骤，可生成 2–3 个候选方案并用外部判据择优，不直接接受首个版本（Best-of-N）。

## Phase 2：分步执行—验证循环

对每个步骤依次执行：

1. 执行该步骤。
2. 立即按完成判据检查产出：运行脚本、抽样核对、与规格或原始数据比对。检查必须基于实际观察，不凭印象。
3. 未通过：在本步内修正重做；同一策略失败两次后必须更换策略，并记录失败原因。更换策略后累计失败达 3 次，或判断本步在当前条件下不可完成：状态置为 failed，停止执行，按 Phase 4 的阻塞终止条件处理——报告失败步骤、已尝试策略与全部验证输出，请用户决策（降低完成判据 / 绕过该步 / 终止任务）。
4. 通过：更新计划文件中的状态，再进入下一步。

**验证分级**：检查手段按可靠性分为三级——

- **A 级 实测运行**：真实执行命令/代码并观察输出（文献类任务的 A 级对应原文与原始数据复核）；
- **B 级 静态核对**：检索官方文档、grep 比对、抽样核对；
- **C 级 人工审读**：重读产物判断。

有可用运行环境与测试数据时必须达到 A 级，不得以 B/C 级冒充；无法实测时，交付物中对应结论须标注"未经实测"。计划文件中的验证记录须写明手段与证据位置（执行了什么命令、核对了哪个文件），使第三方可复查。

**验证重试优先于反思**：步骤未通过时，修复后首先重跑原验证手段确认结果；只有当验证输出不足以定位问题时才动用反思分析，且反思结论必须能回溯到具体的验证输出。

禁止"先全部做完再统一检查"；每步必须先验证再推进。

## Phase 3：整体审查与对抗性反驳

进入本阶段的前提是全部步骤状态为 verified；存在 failed 步骤时不得进入整体审查，直接按 Phase 4 的阻塞终止条件处理。前提满足后：

1. **标准核验**：对照验收标准逐条核验，给出每条是否满足及证据。核验必须基于重新读取产物原文与证据文件，不凭上下文中的记忆下结论；对已修改过的部分，须读取修改后的版本再判断。
2. **信号先于诊断**：所有反驳意见必须先引用原始验证信号（命令回显、测试报告、检索结果、数据摘录），再给出诊断；每条诊断须注明其锚定的信号位置。禁止脱离证据的自由归因——虚构的失败归因会被后续轮次当作事实固化（文献称 memory confabulation）。
3. **独立批判者**：交付级或高风险任务中，具备子智能体能力时须派一个不带生成过程上下文的批判者，仅凭产物、验收标准与原始信号独立审查，其意见与自审结果合并处理；低风险内部任务可用自审加清单替代，但须在简报中声明批判者缺位；介于两者之间的任务默认派批判者，除非用户明确要求从简。子智能体调用失败时重试一次，仍失败则降级为自审并如实声明。批判输出固定为四段式：结论（通过/不通过/不适用）→ 问题定位 → 分析 → 修复建议。干预强度须校准，只报告确证的问题，不为凑数过度批评。
4. **对抗性自审**：按 references/critique-angles.md 中对应领域的清单逐项质问，找出最薄弱的环节。
5. **事实断言抽检**：科研写作类产物中的高风险事实断言（数值、引文、结论性表述），须以独立检索或复算做一致性核对；无法外部核对时声明"未外部核对"。
6. **评审非终局**：自审与单一批判者的结论均不视为终局真理；关键分歧（与批判者结论冲突，或涉及高风险结论）须引入第二种独立视角或外部证据裁决。
7. 区分实测证据、推断与假设；每条反驳意见必须具体、可执行，不接受"整体不错"式的空泛结论。

## Phase 4：迭代优化

- 将反驳意见转化为编号修改清单，逐条处理；每条处理后说明改动与理由。
- 回归验证：每处修改落地后判断其影响范围，受影响的已完成步骤状态重置为 in-progress 并重新验证，防止修复引入新错误（迭代震荡）。
- 修改完成后回到 Phase 3 重新审查，进入下一轮。
- 轮次定义：每执行一次完整的 Phase 3 审查记为 1 轮，首轮审查即第 1 轮；"连续两轮无新增有效批评"指相邻两次 Phase 3 审查（第 N 轮与第 N+1 轮）均无新增。
- 需求变更：执行期间用户变更目标或验收标准，立即停止当前循环，回到 Phase 0 重新确认，受影响步骤的状态重置。
- 终止条件：
  - 全部验收标准满足 → 报告每条标准的达标证据，结束。
  - 反驳收敛 → 连续两轮审查无新增有效批评意见（与 references/critique-angles.md 的收敛规则一致），判定自审收敛，如实报告剩余风险后结束，不必用尽轮次。
  - 轮次用尽仍未达标 → 报告现状、未达标项及原因、建议的下一步，请用户决策。
  - 出现需用户决策的阻塞（权限、资源、方向性选择）→ 立即停止并报告。
- 每轮结束向用户简报：本轮发现的问题、修复内容、剩余风险，以及各关键结论的验证等级（A/B/C）。

## 禁止事项

- 不伪造检查结果、运行输出、数据或引文；无法验证时明示"未验证"。
- 不跳过验证直接推进，不以"应该没问题"替代检查。
- 反驳环节不得流于形式；每轮须逐项排查并产出具体批评意见；若逐项检查后确无新问题，须明确写出"逐项检查未发现新问题"及检查了哪些项。
- 不擅自扩大任务范围；迭代只围绕已确认的验收标准。

## 支持文件

- assets/plan-template.md — 计划追踪文件模板，Phase 1 时复制到任务工作目录填写。
- references/critique-angles.md — 分领域对抗性审查清单，Phase 3 时按任务领域选用。
- scripts/sync-check.ps1 — 维护者工具：比对工作副本与各安装目录的文件哈希，防止副本漂移；路径全部参数化，不随技能执行加载。
- assets/benchmarks/ — 维护者自检基准：预埋已知缺陷的样例任务与答案文件。使用时必须先把任务文件复制到技能目录之外的隔离目录再交给被测执行者，且不得以技能目录内路径形式交付，防止答案泄漏导致测量失效。用于测量批判召回率与精确率，改版后回归测试用。
